# RC.31 Profile completion record and welcome state

New Profile installations write completion record schema 2. The installed Host parser (`js-yaml` with the Host include `entryListSchema`) parses the complete patch; duplicate mapping keys and invalid YAML are rejected. The structured fingerprint preserves sequence order, scalar types and every installed setting, while mapping key order and YAML formatting do not affect it. Non-JSON or shared/cyclic object values are rejected. Only a second patch exactly equal to `{id: ui-settings-general, name: @deepseek-ai/dsh-client-ui-settings-general, config: {welcomeNoticeVersion: '2026-09-28.1'}}` may be removed from the fingerprint. Extra settings, entries, and other notice versions are rejected. This is the state observed from the qualified Host in the 2026-10-29 browser acceptance, and a new Host settings mutation regression exercises the actual persistence path.

Schema 1 Profile records remain subject to their original byte-level SHA-256 check; they are never automatically converted or re-approved on startup. An existing installation whose welcome write changed its patch therefore needs a fresh isolated installation to obtain a schema 2 record. Host records remain schema 1. Package, lock, workspace, dependency graph, artifact and path checks remain in force. Completion records do not authenticate an attacker able to rewrite both record and configuration.
